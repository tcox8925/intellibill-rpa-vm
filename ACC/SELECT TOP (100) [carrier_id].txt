This is the matrix table we have. We start from here : We only process active carriers, so those whose active flag is 1.
1. carrier_id is what we'll use to filter queries on our database or zoho. 
2. carrier_name is what we'll use in our notifications. To show whats been added, processed, success and fail counts.
3. company_id for now is the same for all.
4. process_type will tell you how the carrier runs - one time in a day or if multiple times based on a frequency. If EOD, then one a day at the given eod_time. At that time the carrier should run.
If BATCH and the frequency, then at that frequency (mins). We'll generally take the lowest time mentioned and go from there. We'll have to manage overlaps gracefully.
Generally, the process will start from 8 am CST to 6pm CST. At 8 all BATCH carriers will start. unless eod_time is 8 am (24 hour clock). Now, if carrier A has freq set to 15 mins and B has 30 mins, then at 8am both a and b will run. At 8:15 only carrier A will run. At 8:30 (because lowest freq. is 15 mins), both a and b will run. 
5. We send notifications (a summary notification) at the end of every run. So, the run_id will be the same for all carriers processed in that run. But any error that we record, other than whats defined in the logic that we "handle", we send an alert email -  it will have the carrier name, the error, and then set the active flag to 0. If we have contracts sitting in the queue table, we write it into an csv file with run_id_date.csv, and drop into azure - fixed path. After each run, clear the queue table.
For those we write into templates (to email to carrier), we keep the template design as is (if there are logos, etc.). And this needs us to define in the template, how many rows to skip, and which row number is the header - so we know where to write. While we email it to a carrier, we keep the template name as is - but once sent to carrier, we attach todays date to the name of the template and move it to a folder in azure - fixed path. Again we clear the queue after every run. 
6. Now, origin will tell you where the contracts come from - email will mean there are folders in sharepoint that we'll have to grab. We do this by looking for folder_pattern in the matrix table. crm means we'll query from the crm. 
7. mode is how will the carrier be notified 
8. email_cadence is : if the mode is email, how many times in a day will they have to be emailed. IF it says EOD, its at the end of the day, at the eod_time mentioned. It'll only be once. If its single, then for every contract we process, we send a email.
9. mode_details tells you, if it's template then there's a email template we follow (body of the email). Which will be unique to each carrier.
10. Now if requires_template_update is true, then we'll have mode as email and email_cadence as EOD (required). Now if the process_type is EOD, then like we said the carrier will run just once in that day. If its batch, then we download a copy of the template to a local folder (defined in the matrix table as download_path), and keep appending rows at every run and at the eod_time, we will stop pulling new contracts, process anything in the queue, and add it to the template if successful - and then email it to the carrier if checks are passed. We'll define these checks per carrier. 
11. Some carriers will need us to upload documents to google drive - we'll get the google drive ID from zoho and use the base path from the matrix table and generate the url to open and upload. If link_agent in the matrix table is write then we upload (in this, we need to see if we need to create new folders or use existing or both - what fodlers to create or read will differ with each carrier as will what to upload where), and if it is read (what to read and which foldrs to read will differ with each carrier).
12. email_to is the email to which emails are to be sent to (these are carrier notifications only, not operational).
13. crm_filter shows us when we query the crm, what would be our contract status filter. It can be one or multiple. If its seperated by comma, we generally parse it to OR's. 
14. base_blob_url will show you the base for the folders to be used on Azure Storage. We can add foldr names to this to construct any path.
15. Template name (just the name, we need to add .csv or .xlsx in each carrier handler) shows you the template anme for each carrier.
16. crm_succes_status is what we'll use to update the crm status on success of processing, if needed. It'll be defined for each carrier.
